# Evidência — KAM-132: cobertura Node sobre todo o TypeScript do âmbito

| Campo | Valor |
|---|---|
| Ticket | KAM-132 — Cobertura Node sobre todo o TypeScript do âmbito (`--test-coverage-include`) |
| Ramo | `feature/KAM-132-cobertura-de-todo-o-typescript`, a partir de `main` (`7015cbf`) |
| Data | 2026-10-12 |
| Máquina | Windows 11; Docker 29.7.2 (`linux/amd64`); Node 24.21.0 e Python 3.13.5 em contentor (`node:24.21.0-trixie-slim`), porque não há `node` nem `make` no *host* |

Este ficheiro guarda **o que foi medido**, com o comando ao lado. O «antes» e o
«depois» são do **mesmo código de testes e das mesmas dependências**: a única
diferença entre os dois é o estado de cinco ficheiros (`Makefile`,
`ci/thresholds.yaml`, `tools/coverage_gate.py` e as duas baterias), repostos na
versão de `origin/main` para o «antes».

## 1. Como se reproduz

Na raiz do repositório, num ambiente com `make`, `node` 24.21.0 e o `.venv` do
`make bootstrap`:

```sh
make ci-4
```

O número que o ticket pede é a linha `restante` do resumo que o
`tools/coverage_gate.py` imprime: percentagem, linhas cobertas, total de linhas
e número de ficheiros.

Para separar o efeito da injecção do resto, o mesmo LCOV avalia-se nas duas
réguas sem voltar a correr a *suite*:

```sh
python tools/coverage_gate.py --root .                  # com o universo (o gate)
python tools/coverage_gate.py --root . --sem-universo   # como antes do KAM-132
```

Sem `make` no *host*, foi assim que correu:

```sh
docker run -d --name kamba132 -v '<raiz>:/repo' -w /repo node:24.21.0-trixie-slim sleep infinity
docker exec kamba132 bash -c 'apt-get update -qq && apt-get install -y -qq make python3 python3-venv git'
docker exec kamba132 bash -c 'cd /repo && corepack enable && pnpm install --frozen-lockfile --ignore-scripts && pnpm run build'
docker exec kamba132 bash -c 'cd /repo && make ci-4'
```

> **A medição não correu sobre o volume montado.** As *suites* de `tools/`
> copiam árvores inteiras em cada teste, e o sistema de ficheiros do Windows
> visto de dentro do contentor é lento para muitos ficheiros pequenos. A árvore
> de fontes foi copiada para o disco do contentor (`/work`) e medida lá. O
> comando é o mesmo; o que muda é onde o `make` corre.

## 2. O que a *flag* do Node faz, e o que não faz

O ticket parte de que `--test-coverage-include` resolve o problema. **Não
resolve**, e esta é a medição que o mostra, no Node 24.21.0 que o
`.node-version` fixa. Em `packages/core-ts`, com `tests/health.test.ts`, que
carrega um único ficheiro de `src/`:

| `--test-coverage-include` | Ficheiros no LCOV |
|---|---|
| (sem a *flag*) | 1 — `src/index.ts` |
| `src/**` | 1 — `src/index.ts` |
| `src/**/*.ts` | 1 — `src/index.ts` |
| `src/*` | 1 — `src/index.ts` |
| `./src/**` | **0** |
| `src/storage/motor.ts` (que nenhum teste carrega) | **0** |

Três leituras, todas por execução:

- **A *flag* filtra, não acrescenta.** Com um padrão que só bate num ficheiro
  nunca carregado, o relatório fica **vazio** em vez de ganhar esse ficheiro a
  0%. Está escrito no próprio Node, em
  `lib/internal/test_runner/coverage.js`: «This check filters out files that do
  not match the include globs».
- **Um `./` à cabeça faz o padrão não bater em nada.** É a armadilha de
  semântica de *glob* que os Detalhes Técnicos do ticket nomeiam, e é a razão
  pela qual o `make coverage-node` passa **caminhos exactos** e não *globs*.
- **E por isso a *flag* de inclusão não se usa.** A primeira versão deste
  ticket passava-lhe o âmbito, para o LCOV ficar igual ao que o *gate* conta. A
  revisão adversarial mostrou o custo: a inclusão retira do relatório tudo o
  que não esteja na lista, e um ficheiro que **nenhum estrato classifica** não
  está nela — logo deixava de chegar ao *gate* e deixava de o falhar, contra o
  critério 7 do próprio ticket. Reproduzido com `packages/core-ts/fora.ts`
  carregado por um teste:

  ```text
  fora.ts no LCOV:  sem a flag 1 | com a flag de inclusao 0
  o gate:           sem a flag → "1 ficheiro(s) medidos e nao classificados"
                    com a flag → nenhum achado desse tipo
  ```

  O que o `make coverage-node` passa é **`--test-coverage-exclude`** com os
  ficheiros que os `excluidos` do `ci/thresholds.yaml` já não contam, pedidos a
  `coverage_gate.py --exclusoes-node <pacote>`. Exclui-se o que não conta, em
  vez de se incluir só o que conta.

O comando que reproduz a tabela:

```sh
cd packages/core-ts
node --test --experimental-test-coverage --test-coverage-include='src/storage/motor.ts' \
  --test-reporter=lcov --test-reporter-destination=/tmp/p.lcov tests/health.test.ts
grep -c '^SF:' /tmp/p.lcov
```

E a confirmação de que o código do Node diz o mesmo:

```sh
node --expose-internals -e "const s=process.binding('natives')['internal/test_runner/coverage']; \
  console.log(s.split('\n').filter(l=>/include/i.test(l)).join('\n'));"
```

## 3. O `LF` do Node é o número de linhas do ficheiro

É o que torna a injecção a 0% uma leitura da régua do Node e não uma régua
nossa. Medido nos 23 ficheiros de `packages/core-ts/src/` em medição, com uma
pré-carga que os importa todos: o `LF` de cada um é exactamente o seu `wc -l`.

| Ficheiro | `LF` | `wc -l` |
|---|---|---|
| `src/storage/motor.ts` (só tipos e comentários) | 67 | 67 |
| `src/storage/index.ts` | 70 | 70 |
| `src/identity/index.ts` | 108 | 108 |
| `src/identity/chaves.ts` | 407 | 407 |
| `src/storage/s3.ts` | 450 | 450 |
| `src/logger/index.ts` | 403 | 403 |

Daqui saem três coisas:

- Um ficheiro do âmbito que nenhum relatório mediu entra com `0/<nº de linhas>`,
  que é o que o Node lhe daria.
- **A cobertura de linhas do Node conta comentários e linhas vazias**, e
  portanto infla a percentagem de código muito comentado — `motor.ts` sai
  `67/67` (100%) por ter sido carregado, sem ter um único teste. Fica registado
  como lacuna 23 em [`../ci.md`](../ci.md) §7: o KAM-132 igualou o **universo**
  medido, não a definição de «linha».
- **A contagem é pelos terminadores de linha do JavaScript**, e não pelo
  `str.splitlines` do Python, que divide também em `\x0b`, `\x0c` e `\x85`. A
  revisão adversarial mediu a diferença: um ficheiro de cinco linhas com um
  *form feed*, um *vertical tab* e um NEL dentro de literais sai `LF:5` do Node
  e dava **8** pelo `splitlines`.

## 4. O número antes e depois

Duas medições, e a primeira é a que decide: o par do CI sobre o mesmo conjunto
de relatórios, e o par com `make ci-4` inteiro à mão, que também exercita a
cablagem do alvo.

### 4.1 Os números do CI, que são os que decidem

O `docs/ci.md` §8 fixou a regra depois de a revisão do KAM-002 ter medido o
*gate* 11 numa árvore de trabalho e obtido outro número: **os números que
contam são os do CI**, que é a árvore que decide se um PR passa. Estes são do
*run* [38304958677](https://github.com/albinoJimy/kamba/actions/runs/38304958677)
sobre `73cb77d`, e são um par perfeito — **o mesmo conjunto de oito relatórios
LCOV, avaliado nas duas réguas**, pelo que a única variável é a régua:

| Régua | Estrato | % | Cobertas | Total | Ficheiros |
|---|---|---|---|---|---|
| **antes** (`--sem-universo`) | `restante` | **91%** | 9652 | 10526 | 100 |
| | `critico` | **99%** | 4802 | 4810 | 26 |
| **depois** (o *gate*) | `restante` | **91%** | 9652 | 10526 | 100 |
| | `critico` | **94%** | 4802 | 5055 | 29 |

```sh
gh run download 38304958677 --name cobertura --dir <pasta>
python tools/coverage_gate.py --root . <pasta>/*.lcov                  # depois
python tools/coverage_gate.py --root . --sem-universo <pasta>/*.lcov   # antes
```

**O `restante` é idêntico nas duas réguas**, até à linha: 9652/10526 em 100
ficheiros. É a prova mais directa de que no `restante` não havia **nada**
invisível, e de que os 75% nunca estiveram em risco. Todo o movimento está no
`critico`: 99% → 94%, 245 linhas novas no denominador e 26 → 29 ficheiros.

### 4.2 O par com `make ci-4` completo, que também exercita o `Makefile`

Medido à mão sobre a árvore anterior ao *merge* do KAM-131 (`28f80ef`), com o
alvo inteiro a correr nos dois estados — é o que prova que a cablagem do
`coverage-node` funciona, e não só a avaliação:

| | Estrato | % | Cobertas | Total | Ficheiros |
|---|---|---|---|---|---|
| **antes** (os cinco ficheiros em `dc243e0`) | `restante` | **91%** | 9323 | 10223 | 99 |
| | `critico` | **99%** | 4802 | 4810 | 26 |
| **depois** | `restante` | **91%** | 9418 | 10291 | 99 |
| | `critico` | **94%** | 4802 | 5055 | 29 |

```sh
make ci-4
```

O `critico` reproduz exactamente o do CI. O `restante` difere porque a árvore
difere: o KAM-131, fundido depois desta medição, acrescentou
`tools/scan_secrets/historia.py` ao estrato, que passa de 99 para 100 ficheiros.
**Divergir assim não é defeito**: é o que o §8 do `docs/ci.md` já dizia do
*gate* 11, e é a razão pela qual a §4.1 existe.

Tempos: 521 s e 271 s para os dois `make ci-4` à mão (a diferença é de
aquecimento de caches do contentor, não do *gate*); 2 min 7 s no *job* do CI.

### 4.3 Quatro leituras, e a terceira é a que o ticket não previa

1. **O `critico` desce de 99% para 94%** — 245 linhas novas no denominador, de
   três ficheiros a 0%, e três ficheiros novos na contagem (26 → 29). Fica
   acima dos 90%, com cerca de **250 linhas** de folga: é o estrato que este
   ticket aperta, e isso vai para o dono do *gate* 4 em §7.
2. **O `restante` não se move pela injecção** — no CI é idêntico nas duas
   réguas. No par à mão o seu denominador cresce 68 linhas, e isso é o
   `tools/coverage_gate.py` a crescer com código quase todo coberto pelas
   baterias novas (10223 → 10291, com 9323 → 9418 no numerador), não a
   injecção. O número de ficheiros do estrato é o **mesmo** nos dois estados.
3. **No `restante` não havia nada invisível.** Os 16 ficheiros TypeScript do
   estrato são todos carregados por algum teste; os três que o lado Node nunca
   mediu caem todos no `critico`. O ticket esperava que o `restante` descesse
   «por um valor que ninguém mediu ainda»: mediu-se, e é **zero**. Os 75% nunca
   estiveram em risco, e por isso **nenhum teste novo foi preciso** para os
   manter — o que o ticket pedia era que o limiar não baixasse, e não baixou.
4. **Medem-se menos ficheiros, e isso está certo**: 144 → 141. O
   `--test-coverage-exclude` tira do LCOV o que o `ci/thresholds.yaml` já
   excluía (os *helpers* de `tests/apoio/`, as `fixtures`, os pontos de
   entrada), pelo que os «excluídos» caem de 19 para 13. Não muda número
   nenhum de estrato: os excluídos nunca contaram.

Os três ficheiros que entraram a 0%, pelo nome — é o que o `make ci-4` imprime:

```text
  3 do ambito de ci/thresholds.yaml sem medicao nenhuma, contados a 0% das suas linhas:
    . packages/core-ts/src/identity/index.ts
    . packages/core-ts/src/storage/index.ts
    . packages/core-ts/src/storage/motor.ts
```

São os dois índices de módulo e a costura do motor de armazenamento: nenhum
teste os importa, porque as baterias importam os submódulos directamente. Ficam
a 0% **de propósito** e não se cobriram neste ticket: um teste que apenas os
importasse dava-lhes ~100% sem exercitar comportamento nenhum, porque o `LF` do
Node conta as linhas de `export { … }` e os comentários como atingidas (§3).
Isso seria subir o número sem subir a garantia, que é o defeito que o estrato
existe para apanhar. Ficam nomeados aqui e no PR, para o dono do *gate* 4
decidir se quer uma bateria de superfície para eles.

## 5. A propriedade que o ticket entrega: um módulo sem teste faz o número descer

O critério 1 pede prova por execução: «acrescentar um módulo de ~50 declarações
sem teste faz a percentagem do estrato descer, e o valor da descida fica
registado. Hoje não desce nada».

O módulo de prova tem **50 declarações exportadas** em **355 linhas**, vive em
`packages/core-ts/src/amostra_sem_teste.ts` (estrato `restante`, por
`packages/*/src/**`) e **nenhum teste o importa**. Não entra no repositório: é
criado, medido e apagado pelo mesmo comando.

Não corre no CI — exige pôr um ficheiro na árvore —, pelo que corre à mão sobre
a mesma base da §4.2 (`28f80ef`). Para que a única variável seja o módulo e a
régua, os quatro números saem do **mesmo** conjunto de relatórios Python, e só o
lado Node é remedido:

| | Módulo | Régua | `restante` | Cobertas | Total | Ficheiros |
|---|---|---|---|---|---|---|
| **A** | não | antiga (`--sem-universo`) | 91% | 9418 | 10291 | 99 |
| **B** | **sim** | antiga (`--sem-universo`) | **91%** | 9418 | 10291 | **99** |
| **C** | não | nova (o *gate*) | 91% | 9418 | 10291 | 99 |
| **D** | **sim** | nova (o *gate*) | **88%** | 9418 | **10646** | **100** |

```sh
# sem o módulo
make coverage-node
python tools/coverage_gate.py --root . --sem-universo   # A
python tools/coverage_gate.py --root .                  # C
# com o módulo
cp <modulo> packages/core-ts/src/amostra_sem_teste.ts
make coverage-node
python tools/coverage_gate.py --root . --sem-universo   # B
python tools/coverage_gate.py --root .                  # D
```

**A → B é a medição do «hoje não desce nada».** Com a régua antiga, 355 linhas
de TypeScript sem um único teste deixam os três números **byte a byte iguais**:
91%, 9418/10291, 99 ficheiros. O módulo é invisível porque o V8 só reporta o que
foi carregado.

**C → D é a propriedade entregue.** O estrato desce **3 pontos**, de 91% para
88%; o denominador cresce exactamente as 355 linhas do ficheiro (10291 → 10646)
e a contagem de ficheiros passa de 99 para 100. O `make ci-4` nomeia-o:

```text
  4 do ambito de ci/thresholds.yaml sem medicao nenhuma, contados a 0% das suas linhas:
    . packages/core-ts/src/amostra_sem_teste.ts
    . packages/core-ts/src/identity/index.ts
    . packages/core-ts/src/storage/index.ts
    . packages/core-ts/src/storage/motor.ts
```

Uma medição anterior, com o mesmo módulo em **17** declarações e 124 linhas, deu
a mesma propriedade com menor amplitude: `restante` de 91% para 90%, denominador
de 10175 para 10299 (sobre a base anterior ao *merge*). Fica registada porque
diz o que o limiar agregado aguenta: com 9418 linhas cobertas, descer abaixo de
75% exige mais de 2300 linhas não cobertas de uma vez — ou seja, **o número
desce, e o *gate* só fica vermelho quando a dívida é grande**. É a lacuna 7 de
[`../ci.md`](../ci.md) §7 (granularidade do limiar), que este ticket não fecha
por ser decisão do canon.

## 6. Prova por mutação

```sh
python tools/lint_arch/tests/mutacoes.py --aplicaveis   # 17 mutacoes, 0 nao aplicaveis
python tools/lint_arch/tests/mutacoes.py                # 17 apanhadas, 0 sobreviventes
```

**24 mutações, 24 apanhadas, 0 sobreviventes**, com linha de base verde. Cada
uma introduz um defeito nomeado e exige que as duas baterias fiquem vermelhas:
o ficheiro sem medição deixa de entrar no denominador; entra como se estivesse
coberto; quem entrou a 0% deixa de sair pelo nome; os `excluidos` deixam de
valer na injecção; um ficheiro sem estrato passa a ser injectado; o universo
volta a deixar fugir tudo o que não seja `.ts`; volta a percorrer a árvore
inteira em vez das raízes dos padrões; sem raiz literal mede zero em silêncio;
a contagem de linhas volta ao `splitlines`; um pacote sem ficheiros no âmbito
deixa de ser erro; um caminho com espaço passa em silêncio; o `node --test`
deixa de receber a lista; a lista passa a ser escrita à mão no `Makefile`; volta
a filtrar pelo âmbito em vez de excluir; o limiar do `restante` baixa para 50; o
serviço de identidade e os pontos de entrada deixam de estar excluídos.

**Sete delas nasceram da revisão adversarial**, e uma sobreviveu à primeira
execução: «as pastas com ponto à cabeça contam como código» só foi apanhada
depois de a bateria ganhar uma pasta de ferramenta **dentro** de uma raiz do
âmbito — a regra do ponto tinha deixado de ser exercitada quando o universo
passou a procurar só nas raízes.

**Porque não estão em `db/mutacoes.py`.** Aquele é o arreio dos *gates* de base
de dados: copia `db/`, `libs/py-core/`, `ci/` e `packages/core-ts/` e corre
`db/gate_bd.py` contra um PostgreSQL descartável. Não exercita o
`tools/coverage_gate.py` nem o `Makefile`, pelo que uma mutação do *gate* 4
posta lá sobreviveria **por construção** — daria por provado o que nunca
correu. Vivem onde vive o código, como a do *logger*
(`tools/log_policy/tests/mutacoes.py`) e a da cadeia de fornecimento
(`tools/supply_chain/canario.py`).

As 24 incluem sete que nasceram da revisão adversarial. As 114 mutações de base de dados continuam todas aplicáveis depois deste *diff*
(`python db/mutacoes.py --aplicaveis` → «114 mutacao(oes) conferida(s), 0 nao
aplicavel(is)»). A lista completa não foi corrida à mão: o *diff* não toca em
nenhum ficheiro que alguma delas altere, e desde o KAM-143 ela corre na tarefa
nocturna.

## 7. A decisão que se devolve ao dono do *gate* 4

**O estrato que este ticket aperta é o `critico`, e não o `restante`.** Fica em
94% contra um mínimo de 90%: cerca de **250 linhas** de folga. Três dos seus 29
ficheiros estão a 0% por nenhum teste os importar —
`packages/core-ts/src/identity/index.ts` (108 linhas),
`packages/core-ts/src/storage/index.ts` (70) e
`packages/core-ts/src/storage/motor.ts` (67). Dois ou três módulos novos sem
cobertura em `*/identity/*`, `*/storage/*`, `*/logger/*`, `*/tenant_guard/*`,
`*/pagamentos/*` ou `*/validador/*` põem o *gate* vermelho — e o ticket que os
trouxer vai encontrar uma dívida que não é dele.

Há duas saídas, e nenhuma é do executor deste ticket:

1. **Uma bateria de superfície para os três** — importa cada índice de módulo e
   assere que cada nome esperado está exportado. É um teste real (apanha um
   `export` perdido numa refactorização), mas o seu efeito na percentagem é
   quase todo artificial: o `LF` do Node conta as linhas de `export { … }` e os
   comentários como atingidas, pelo que os três passariam de 0% a ~100% sem que
   nenhum comportamento ficasse exercitado. Subir o número sem subir a garantia
   é o que o estrato existe para não premiar.
2. **Declarar os três como excluídos**, com a razão escrita, como já está
   `packages/core-ts/src/identity/contactos.ts`. Honesto, e tira-os do
   denominador — mas são a superfície pública de dois módulos do estrato
   `critico`, e excluí-los é dizer que não se exige cobertura à superfície.

Não se escolheu nenhuma: as duas mudam o que o limiar de 90% significa, e o
limiar é *proposta* do `specs/01` §4.1. Fica medido, nomeado, e com as duas
opções escritas.
