## 1. O que «verificado» quer dizer nos runbooks

Um comando marcado `verificado` correu **nas imagens que o compose de produção fixa**,
por *digest*, com a configuração do repositório, num contentor isolado desta máquina
(nomes `kam083-*`, rede própria, apagados no fim). A forma `docker compose -f … exec
<serviço>` dos runbooks é a mesma chamada ao mesmo binário; o que **não** se verificou foi
o compose de produção a correr, pela razão do §5, achado 1.

| Imagem (a do compose) | O que se verificou |
|---|---|
| `prom/prometheus:v3.7.3@sha256:4921…` com `prometheus.yml` e `regras/` do repositório | `promtool query instant http://127.0.0.1:9090 '<expr>'` para as onze expressões dos runbooks — todas aceites pelo *parser*; a de controlo `sum by (x (` dá `parse error`. Com o GWY ausente, o `ingress_parado` passou a `firing` (via `/api/v1/rules`) |
| `prom/alertmanager:v0.28.1@sha256:27c4…` com o `alertmanager.yml` do repositório | `amtool --alertmanager.url=http://127.0.0.1:9093 alert query`, `silence add … --duration --author --comment`, `silence query`, `silence expire <id>`, `config routes show` (a árvore saiu com os três *receivers* por severidade) |
| `pgvector/pgvector:0.8.7-pg18@sha256:2358…` | `pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"` («accepting connections»), `SELECT pg_is_in_recovery()` (`f`), `df -h /var/lib/postgresql` |
| `valkey/valkey:9.1.2-trixie@sha256:4186…` | `valkey-cli ping`, `LLEN bull:wa-inbound:wait`, `ZCARD bull:wa-inbound:failed`. A forma `bull:<fila>:wait` é a que a suite `db/tests_eventos` do *gate* 8 lê |
| `ghcr.io/berriai/litellm:v1.104.2@sha256:3d88…` com `llm/litellm.config.yaml` | `/health/liveliness` → 200; `/health/readiness` → `{"status":"healthy","db":"Not connected"}`; `/key/generate`, `/key/list`, `/key/update` → **500** (achado 2) |

E o que fica `não verificado` em todos os runbooks, com a mesma razão: `docker compose
ps|logs|restart|up` contra o compose de produção, o `pgbackrest` na forma do compose (o
serviço que o correrá não existe, D1/KAM-105), o `doppler run` (sem conta), e qualquer
interacção com a Meta, o facilitador ou um fornecedor de LLM.

## 2. As consultas SQL, contra uma base migrada

Base descartável na imagem do compose, com os papéis do `db/bootstrap.py` e as migrações
até à cabeça:

```text
python db/bootstrap.py                                   -> papeis criados, kamba_pay_hooks incluido
python -m alembic -c migrations/alembic.ini upgrade head -> ... 0038 -> 0039 (KAM-060)
```

Cada consulta dos runbooks correu **na forma exacta do runbook** (`sh -c 'psql -U
"$POSTGRES_USER" -d "$POSTGRES_DB" -c "…"'`), com um `tenant_id` sintético:

| Runbook | Consultas | Resultado |
|---|---|---|
| RB-K02 | cobranças à espera; *callbacks* por hora; DLQ de `payment.*`; reservas a expirar | as quatro correm (0 linhas) |
| RB-K03 | `dat.llm_call_log` por fornecedor e desfecho | corre (0 linhas) — **depois de corrigida**: a primeira versão filtrava por `criado_at`, que não existe; a coluna é `ts` |
| RB-K04 | canal do *tenant*; *templates* pausados e registo de qualidade; `UPDATE … estado = 'suspenso'` com `SET ROLE kamba_batch` | as três correm; o `UPDATE` dentro de `BEGIN … ROLLBACK` deu `UPDATE 0` sem erro de permissão |
| RB-K05 | canais acima de 800 no mês (`platform.ten_periodo(now())` = `2026-11-01`) | corre (0 linhas) |
| RB-K06 | canal com coexistência; `account_update` de 7 dias | as duas correm (0 linhas) |
| RB-K09 | custo por *tenant* em 24 h; conversas activas por *tenant* | as duas correm (0 linhas) |

O erro do `criado_at` é a razão de esta secção existir: uma consulta escrita a partir da
leitura do esquema tinha uma coluna inventada, e só correr a apanhou. Também se
confirmou na base a função `platform.manual_confirmar(uuid,uuid,text,bigint)` que o RB-K02
cita, e o domínio de `platform.conversations.mode` (`bot`, `dono`, `humano`, `pausada`)
que o RB-K09 usa.

```text
cd tools && python -m scan_secrets --root .. files <os 16 ficheiros do ramo>
  -> scan_secrets: limpo, 16 ficheiro(s); saida 0
grep -nE '\+?244 ?9[0-9]{8}|"\+[0-9]{9,15}"|\b9[0-9]{8}\b' <os mesmos>
  -> sem ocorrencias (saida 1)
```

Os padrões de telefone são os do varredor do *gate* 7 (`tools/meta-sim/src/numeros.ts`)
mais a sequência de nove dígitos do X-11. **O X-11 (`log_policy x11`) não serve para
Markdown**: classifica cada linha que não seja JSON como `linha_fora_do_formato` (2418
achados em 2396 linhas, todos desse tipo), e não se usou como prova. Nenhum runbook tem
nome de pessoa, número, endereço de e-mail ou *endpoint* interno real: os contactos são
papéis e canais, e os segredos citam-se pelo nome da entrada do inventário.
