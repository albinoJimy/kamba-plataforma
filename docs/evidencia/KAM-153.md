## 2. O identificador não se escolhe

Esta secção foi reescrita duas vezes, por duas razões diferentes, e as duas
reescritas valem mais do que o resultado.

### A primeira versão: uma corrida apresentada como apuramento

O `main` de então tinha o 143 por maior. A primeira versão varreu **todos** os
ramos, locais e remotos, e os PRs abertos, viu que o 144 estava tomado por
trabalho não fundido, tomou o 145 e escreveu que estava «livre em todos os
ramos».

**Estava livre quando foi varrido, e deixou de estar cinco segundos depois.**
Três sessões escolheram o 145 em dez segundos, cada uma escrevendo-o na mesma
linha dos mesmos dois ficheiros; uma delas abriu ainda o 146 e o 147. A primeira
revisão adversarial apanhou-o com o mesmo comando que o documento transcrevia
como prova.

A lição que ficou dessa reescrita — **varrer *refs* é uma corrida, não uma
reserva** — está certa, mas a conclusão que se tirou dela estava errada: a
segunda versão saltou para o 148, três acima do maior do `main`.

### A segunda versão: o gate 4 reprovou o salto

```text
FALHA: lint_refs
FAIL: test_kam_cobre_o_backlog_inteiro_sem_buracos
```

O teste é de três linhas e é categórico:

```python
numeros = sorted(int(x[4:]) for x in self.conjuntos.kam)
self.assertEqual(numeros[0], 1)
self.assertEqual(numeros, list(range(1, numeros[-1] + 1)), "o backlog nao tem buracos")
```

**Não existe «próximo número livre» neste repositório.** O conjunto lido do §4
tem de ser `1..máximo`, sem buracos, e o gate 3 reprova quem *cite* um
identificador que não esteja no §4. As duas regras juntas deixam exactamente uma
escolha: **o seguinte ao maior do `main`**. Tudo o que a primeira versão
construiu sobre «varrer os ramos» era arquitectura sobre uma premissa falsa — a
varredura é útil para *saber com quem se vai colidir*, nunca para escolher.

### O que isto implica, e que não é um descuido de ninguém

**Ramos concorrentes colidem sempre neste número, por construção.** Não há
escolha que o evite: dois PRs abertos ao mesmo tempo sobre o mesmo `main` têm
ambos de usar `máximo + 1`. A colisão é mecânica e resolve-se na integração —
quem funde depois renumera o seu ticket e refaz as contagens —, exactamente como
a *skill* já declara para os ficheiros de registo. O que **não** é aceitável é
o que a segunda versão fez: evitar a colisão criando um buraco.

## 4. A busca que fecha a classe

As três linhas eram o sintoma. O que fica é a verificação **ancorada no nome do
anexo** — `E1`–`E5` são cinco nomes fixos em disco, e o prefixo é a parte
variável e defeituosa.

### G6 — a terceira forma tem busca própria

```bash
ls specs/*.md | grep -v EPIC-01 \
  | xargs grep -noE '(^|[^/A-Za-z._-])E[1-5]_[A-Za-z0-9_]+\.md'
```

**3 → 0.** O caractere antes de `E[1-5]` não pode ser `/` nem caractere de
palavra de caminho; sem essa âncora, a busca apanharia as 152 citações que já
estão certas.

### G7 — o resolvedor deixa de depender do prefixo

```python
import os, re, sys
from pathlib import Path

RAIZ = Path(sys.argv[1] if len(sys.argv) > 1 else ".").resolve()
EXCLUIDOS = {"EPIC-01_Fundacoes_Dados.md"}
ANEXO = re.compile(r"E[1-5]_[A-Za-z0-9_]+\.md")
LINK_MD = re.compile(r"\[[^\]\n]*\]\(([^)\s]+)\)")
CARACTER_DE_CAMINHO = re.compile(r"[A-Za-z0-9_./-]")


def resolve_exacto(base: Path, caminho: str) -> bool:
    """Resolve `caminho` a partir de `base` exigindo a grafia exacta."""
    actual = base
    for parte in caminho.split("/"):
        if parte in ("", "."):
            continue
        if parte == "..":
            actual = actual.parent
            continue
        try:
            if parte not in os.listdir(actual):
                return False
        except OSError:
            return False
        actual = actual / parte
    return actual.exists()


ocorrencias, falhas = 0, []
for ficheiro in sorted((RAIZ / "specs").glob("*.md")):
    if ficheiro.name in EXCLUIDOS:
        continue
    for n, linha in enumerate(ficheiro.read_text(encoding="utf-8").splitlines(), 1):
        candidatos, resto = [], linha
        # 1) ligacoes markdown: conta o ALVO, e retira o construto da linha
        for m in LINK_MD.finditer(linha):
            alvo = m.group(1).split("#")[0]
            if ANEXO.search(alvo):
                candidatos.append(alvo)
            resto = resto[: m.start()] + " " * (m.end() - m.start()) + resto[m.end():]
        # 2) o que sobra: caminhada para tras sobre caracteres de caminho
        for m in ANEXO.finditer(resto):
            i = m.start()
            while i > 0 and CARACTER_DE_CAMINHO.match(resto[i - 1]):
                i -= 1
            candidatos.append(resto[i:m.end()])
        for caminho in candidatos:
            ocorrencias += 1
            if not resolve_exacto(ficheiro.parent, caminho):
                falhas.append((f"{ficheiro.relative_to(RAIZ).as_posix()}:{n}", caminho))

print(f"G7: {ocorrencias} citacoes de anexo em forma de nome de ficheiro em "
      f"specs/ (excluido EPIC-01); {len(falhas)} nao resolvem")
for onde, caminho in falhas:
    print(f"  FALHA {onde}  {caminho}")
sys.exit(1 if falhas else 0)
```

|---|---|
| `f4c7e3d` | `G7: 152 citacoes …; 3 nao resolvem`, as três da linha 11 do `specs/EPIC-10` |
| depois | `G7: 152 citacoes …; 0 nao resolvem` |

### Três decisões de desenho, cada uma por uma razão medida

As duas primeiras versões deste resolvedor estavam erradas, e as revisões
apanharam as três.

1. **Estritamente relativo ao ficheiro, e não também à raiz.** A primeira versão
   aceitava as duas posições, por analogia com o resolvedor da `ANALISE-04`, e
   declarava isso «limite declarado, não omissão». Medido: das 152 ocorrências,
   **zero** dependem da resolução a partir da raiz — a permissão não salvava
   nenhuma citação real e aceitava precisamente a forma que a regra de posição do
   KAM-128 declara errada (`docs/tecnica/evidencia/…` sem o `../`), que resolve
   da raiz e **quebra na renderização do GitHub**. Com a resolução estrita, essa
   forma passa de «aceite por desenho» a apanhada, e o `0/152` não muda.
2. **Grafia exacta, componente a componente por `os.listdir`.** O
   `Path.exists()` do Windows é insensível a maiúsculas e o CI corre em Linux:
   sem isto, um `EVIDENCIA/` passava na máquina de quem mede e reprovava no CI.
   Não se usa `Path.resolve()`, que no Windows canonicaliza a grafia e esconde o
   defeito. Verificado à parte: **0** ocorrências com divergência de grafia em
   `specs/` e **0** no repositório inteiro — o defeito não é vivo, mas sem esta
   decisão o `0` era um artefacto da máquina e não uma medição.
3. **O texto de uma ligação markdown não é o seu alvo.** A caminhada para trás
   para no `` ` `` ou no `[`, pelo que o texto de uma ligação era lido como
   caminho e produzia uma **falha falsa**. As ligações tratam-se primeiro, pelo
   alvo. Hoje `specs/` tem **0** ligações markdown a anexo, pelo que o caso não
   é vivo; está tratado porque a forma existe no conjunto fora de `specs/`.

**O gate 3 foi medido três vezes, e as duas primeiras medições eram inválidas.**
A versão anterior deste ficheiro declarava o gate verde com `552 ficheiros`,

distintos, soma da coluna do §3.1 igual a **151**, e **151** em
`specs/INDICE.md` §1 e no `../../README.md`.

O `README.md` dizia **130** quando este trabalho começou. Não era defeito sem
dono: o KAM-144 registou-o como **dívida 19** de
[`../dividas-documentais.md`](../dividas-documentais.md) e decidiu **não** o
corrigir, com a razão escrita — escolher o número é decidir a base de contagem, e
isso é critério do KAM-130, que por sua vez isenta o `README.md` do alvo da sua
busca H4. Entretanto outro ticket actualizou o número e **não riscou a dívida**,
que ficou no ficheiro a citar o valor antigo.

Entretanto a linha de versão 1.14 desse ficheiro passou a dar a dívida como
riscada **sem riscar a linha**, que continuou inteira e a citar valores antigos.
**Este ticket risca-a de facto**, por pedido expresso do fundador
(«actualiza as contagens de §1, §3.1 e `README.md`») e porque a objecção se
resolve **declarando a base** em vez de a adiar: o número é a contagem de linhas
`| KAM-NNN |` do §4 — a mesma base que o §1 e o §3.1 já usam —, derivada no
momento por `grep -c` e não copiada de outro índice. O KAM-130 continua dono da
base de contagem das **outras** grandezas (ADRs, decisões abertas, anexos,
documentos activos). Divergir de uma decisão registada por outro ticket é uma
decisão em si, e está aqui nomeada em vez de feita em silêncio.

### Uma terceira superfície de sincronia, que a medição não cobre

A afirmação «0 divergências» vale para `specs/INDICE.md` §4 ↔ blocos dos epics.
Há uma **terceira** superfície: a §3 «Tabela Resumo de Tickets» de cada epic. No
`EPIC-01` ela tem **28** linhas para **30** tickets — faltam-lhe o KAM-129 e o
KAM-130, que é a dívida **3** de `../dividas-documentais.md`, pré-existente
(**27** para **29** em `f4c7e3d`). Este ticket acrescentou lá a sua linha, como
deve; **não** corrigiu as duas que faltam, que são de quem pagar essa dívida. A
frase «0 divergências» não cobre esta superfície, e dizê-lo é o ponto.

### O que não se verificou, e porquê

- **Nenhuma revisão humana.** As duas revisões adversariais deste ticket são
  produzidas por agentes e **não contam como revisor** para o DoD. A caixa fica
  vazia.
- **`make check` por inteiro e os gates que precisam de Docker ou de Node**
  (gates 4, 6, 8, 9 no CI, 11). O *diff* são seis ficheiros `.md` e não toca em
  código, em configuração de CI, em dependências nem em migrações; correram os
  gates que lêem documentos (3 e 3b), o `lint_arch` e o *scanner* de segredos. A
  prova por mutação não se aplica: mede mutações sobre código, e este ticket não
  altera nenhum ficheiro que alguma mutação altere.
- **O estado do CI no PR**, até ele correr.
- **A adequação dos critérios**, por oposição ao seu cumprimento. Ninguém
  perguntou se os critérios deste bloco cobrem o objectivo — só se o que afirmam
  se mede.

## 6. Decisões, e o que fica devolvido

| # | Decisão | Fundamento |
|---|---|---|
| 1 | **Ancorar a busca no nome do anexo, não no prefixo** | É a única âncora que vê a ausência do prefixo. Qualquer busca ancorada no prefixo mede a população já corrigida — foi assim que três referências atravessaram duas verificações verdes |
| 2 | **Resolver estritamente relativo ao ficheiro, com grafia exacta, e pelo alvo das ligações** | Revertida da primeira versão, que aceitava a raiz e chamava-lhe limite declarado: zero das 152 dependiam disso, e a permissão aceitava a forma que o KAM-128 declara errada. Com as três correcções, o canário apanha duas formas que antes passavam e deixa de dar um falso positivo numa terceira |
| 3 | **Não marcar as caixas CA1 e CA4 do KAM-129** | Depois deste ticket, **zero** caminhos de anexo deixam de resolver em `specs/`. Mas o CA1 não diz isso: diz «sem directório qualificador», e as 9 referências por abreviatura são exactamente isso — corretamente, porque não são caminhos. **À letra, o CA1 continua falso**, e satisfazê-lo exige redefini-lo. Essa é decisão de quem o escreveu; a medição fica aqui, a um passo dela |
| 4 | **Nomear no bloco do KAM-129 as duas formas que faltavam** | A terceira (nome sem prefixo) é defeito e era invisível; a quarta (forma-código nua) é legítima e **não** é caminho. Nomear a quarta é tão importante como nomear a terceira: sem isso, o próximo executor «corrige» 9 referências correctas |
| 5 | **Não corrigir os ~43 caminhos de entregas futuras** | A decisão em aberto é de redacção do DoD («qual é a lista declarada de artefactos futuros»), não um defeito de referência; corrigi-los exigiria criar ficheiros que nenhum ticket pediu. Fica devolvida a quem escreveu a caixa, como o achado ADV-02-04 já pedia |
| 6 | **Não acrescentar gate de CI sobre caminhos em *code-span*** | Depende da decisão 5: um gate assim reprovaria hoje nos ~43. E, medido, exigiria **três** exclusões e não uma — fora de `specs/` a classe falha também no anexo de análise que inventariou o defeito e neste ficheiro, que transcreve o canário. Dizer que o ticket «não tem gate» é mais honesto do que ligar um gate com uma lista de excepções a cobrir uma decisão que ninguém tomou |
| 7 | **Os intervalos de série voltam a ser contíguos** | A segunda versão escrevia-os descontínuos para contornar o gate 3, que expande intervalos e reprovava ao ver um identificador inexistente. Era sintoma do buraco, não convenção: com o identificador a ser `máximo + 1`, o intervalo contíguo é verdadeiro e o gate não tem nada a dizer |
| 8 | **Resíduos para `../dividas-documentais.md`, não para ticket** | A linha de versão 1.13 que falta no `EPIC-01` e o campo `Versão` do cabeçalho dos onze epics parado em `1.0` (sete com a tabela à frente, quatro sem desvio): nenhum pede código, e o segundo pede primeiro que se decida o que o campo significa. `../../specs/01_Engineering_Standards_e_Handoff.md` §6, princípio 1 |
| 9 | **O identificador é `máximo do main + 1`, e a colisão entre ramos é estrutural** | Não há «próximo livre» a escolher: o teste de buracos do gate 4 e o gate 3 deixam uma só opção. Varrer os ramos serve para saber com quem se vai colidir, nunca para escolher. A colisão resolve-se na integração, renumerando quem fundir depois — e evitá-la com um buraco reprova o PR, que é como esta decisão foi aprendida |
| 10 | **Pagar a dívida 19 e riscar a linha, divergindo do KAM-144** | O pedido do fundador nomeia as três contagens, e a objecção registada («escolher o número é decidir a base») resolve-se declarando a base, que é a mesma que o §1 e o §3.1 já usam. Está nomeado como divergência em vez de feito em silêncio |
