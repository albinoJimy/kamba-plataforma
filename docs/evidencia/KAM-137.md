## 1. O ponto de partida

### 1.1 O *ruleset* efectivo lê-se, e a credencial que o lê

```
$ gh auth status
github.com
  ✓ Logged in to github.com account albinoJimy (keyring)
  - Token scopes: 'gist', 'read:org', 'repo', 'workflow'
```

```
$ gh api repos/albinoJimy/kamba --jq '.permissions.admin'
true
```

A credencial usada nesta medição é a sessão `gh` do fundador, que tem
administração do repositório. **Não é a credencial que o ADR desenha**: o ADR
pede um *fine-grained token* com `Administration: Read-only` e nada mais, e
criá-lo é acto do fundador. O que se mediu aqui vale para o caminho de leitura;
que o caminho funcione com uma credencial **só** de leitura fica
**NÃO VERIFICADO**, e valida-se criando o *token* do ADR, exportando-o em
`KAMBA_RULESET_TOKEN` e correndo
`python -m ruleset_check check --root . --transporte http` (§5.7).

### 1.2 O espelho e o efectivo estavam iguais antes de se tocar em nada

```
$ gh api repos/albinoJimy/kamba/rulesets/24879081 --jq '{name,target,enforcement,conditions,rules,bypass_actors}'
```

Comparado em Python com `.github/rulesets/main.json`:

```
iguais campo a campo: True
chaves exportacao: ['bypass_actors', 'conditions', 'enforcement', 'name', 'rules', 'target']
chaves ficheiro   : ['bypass_actors', 'conditions', 'enforcement', 'name', 'rules', 'target']
texto identico    : True
```

A última linha é o critério 9: o comando de exportação do `README.md`, passado
por `json.dumps(..., indent=2, ensure_ascii=False, sort_keys=True)` mais uma
quebra de linha, **reproduz o ficheiro byte a byte**. O `id` (`24879081`) está
ao lado do comando no `README.md` e em
[`../../ci/ruleset.yaml`](../../ci/ruleset.yaml), e há um teste que confronta
os dois (`TestConfiguracao::test_cada_id_declarado_esta_no_readme_do_ruleset`),
mais um que exige que **cada alvo** declarado esteja nomeado no `README.md`.

**E o `mostrar` passou a produzir esse formato.** A revisão adversarial notou
que a *docstring* convidava a usá-lo para actualizar o espelho e que a saída
não servia para isso — imprimia a forma normalizada interna, com os contextos
como pares. Hoje imprime os seis campos de política como o ficheiro os guarda:

```
$ python -m ruleset_check mostrar --root . --repositorio albinoJimy/kamba > /tmp/x
mostrar == espelho, byte a byte: True
```

É o que torna possível actualizar o espelho sem decorar o `id` nem a
reformatação — e é a única forma prática de o fazer para o
`albinoJimy/kamba-plataforma`, cujo `id` ainda não existe
(`TestMostrar::test_produz_o_formato_exacto_do_espelho`).

## 2. O que se compara, e o que fica de fora

Da lista do critério 4, à letra. O código está em
`tools/ruleset_check/comparador.py`, e cada linha desta tabela tem teste.

| Comparado | Onde |
|---|---|
| `enforcement` (`active`) | `CAMPOS_DE_TOPO` |
| `name`, `target` | `CAMPOS_DE_TOPO` |
| `conditions` (`ref_name.include` / `.exclude`, ordem irrelevante) | `CAMPOS_DE_TOPO` |
| `bypass_actors` **vazio** | `CAMPOS_DE_TOPO` + regra própria |
| `rules.pull_request` — 8 parâmetros | `PARAMETROS_DE_POLITICA` |
| `rules.required_status_checks` — `strict_required_status_checks_policy`, `do_not_enforce_on_create`, e **os sete contextos** | `PARAMETROS_DE_POLITICA` |
| `rules.deletion` | `PARAMETROS_DE_POLITICA` |
| `rules.non_fast_forward` | `PARAMETROS_DE_POLITICA` |

**Os oito campos voláteis ignorados, nomeados um a um**, com a razão em
`comparador.VOLATEIS`:

| Campo | Porque não é política |
|---|---|
| `id` | identificador atribuído pelo GitHub; vive no `ci/ruleset.yaml`, não no espelho |
| `node_id` | identificador opaco da API GraphQL |
| `source` | o repositório de onde o *ruleset* vem; é contexto |
| `source_type` | `Repository` ou `Organization`; é contexto |
| `created_at` | carimbo de criação |
| `updated_at` | carimbo da última alteração; muda em edições que não mudam política |
| `current_user_can_bypass` | depende de **quem** pergunta: dois leitores vêem valores diferentes do mesmo *ruleset* |
| `_links` | hiperligações de navegação da API |

**Três propriedades que não estavam no critério e que fecham buracos da lista:**

- um campo de topo que a API passe a devolver e que **não esteja em nenhuma das
  duas listas falha** (`campo-novo-na-api`). Sem isto, uma política nova num
  campo novo entrava em silêncio;
- um campo de política **ausente dos dois lados** é divergência
  (`campo-de-politica-ausente`), e não «igual a si próprio»;
- um `bypass_actors` não vazio **no GitHub** é vermelho mesmo que alguém o
  acrescente também ao ficheiro. O ficheiro não é autoridade para conceder
  *bypass*.

**Dois valores comparados como estão, e não como «deviam ser»:**
`required_approving_review_count: 0` (cedência registada na lacuna 16 do
`../ci.md` §7) e `strict_required_status_checks_policy: false` (deliberado,
justificado no `README.md` do *ruleset*). O comparador compara o GitHub com o
ficheiro; não compara o ficheiro com uma opinião.

**E quatro divergências que não são sobre campos, mas sobre a existência da
coisa** — acrescentadas ao fechar o bloqueador C1, e produzidas por
`verificacao.py` antes de o comparador chegar a correr:

| Regra | Quando |
|---|---|
| `repositorio-sem-ruleset` | o repositório não tem *ruleset* nenhum |
| `ruleset-ausente` | tem *rulesets*, e nenhum com o `name` do espelho |
| `ruleset-ambiguo` | tem mais do que um com esse nome; não se escolhe por adivinhação |
| `id-do-ruleset-divergente` | o `ruleset_id` declarado não é o que o nome resolve — o *ruleset* foi apagado e feito de novo |

As quatro são **saída 1 e não 2**, e a distinção é o criterio 5 ao contrário:
a leitura correu, e a resposta foi que a política não está aplicada. Dizer «não
verifiquei» seria tão falso como dizer «conforme».

**A revisão adversarial não mexeu nesta parte, e vale registá-lo:** o
comparador, o *fail-closed* e a lista comparada resistiram a 15 mutações de 15,
a 15 variantes de falha de ambiente todas a sair 2, e aos oito campos voláteis
confirmados um a um como não-política. O que ela partiu foi o que estava **à
volta** desta parte — sobre que repositório ela corria.

### 3.1 A guarda «só leitura», reescrita depois de ser reprovada

A primeira versão desta garantia **não a sustentava**, e a revisão adversarial
demonstrou-o: procurava `POST`, `PUT`, `PATCH` e `DELETE` em literais, em
maiúsculas, e dois dos três testes liam **só** o `api.py`. Injectou cinco
caminhos de escrita, e os cinco passaram:

| Injecção | Porque passava | Regra que agora a apanha |
|---|---|---|
| `urllib.request.Request(url, data=corpo)` | `POST` implícito, sem a palavra | `pedido-com-corpo` |
| `os.system("curl -d ...")` | nenhum verbo, e `cli.py` nem era lido | `comando-do-sistema` |
| `verbo = "PU" + "T"` | a concatenação esconde a palavra | `verbo-de-escrita`, com as constantes dobradas |
| `subprocess.run(["gh","api",p,"-X","post"])` | minúsculas | `flag-de-metodo` **e** `verbo-de-escrita` |
| `gh ruleset rm` no `cli.py` | ficheiro não lido | `subprocesso-fora-de-gh-api` |

Os cinco estão agora na suite **como canários**, cada um a exigir a sua regra —
uma guarda que apanhasse tudo pela mesma regra não provava nada sobre as
outras. Há também um **controlo positivo**: o caminho legítimo do próprio
pacote (`subprocess.run(["gh","api",…])`, `Request(…, method="GET")`,
`urlopen(p, timeout=30)`) tem de passar limpo, sem o qual uma guarda que
recusasse tudo «passava».

**E o que ela não garante está escrito nela, e nos seis sítios onde a frase
aparecia.** Isto é uma lista de padrões, não uma prova de ausência: um autor
determinado contorna-a com um nome de função construído em tempo de execução. A
afirmação passou de «não há caminho de escrita» para «não há nenhum caminho de
escrita dos que esta guarda reconhece», e a lista dos padrões está ao lado.
Prometer uma garantia de máquina que não existe é pior do que não a prometer.

### 3.2 A lista de alvos

`test_verificacao.py` existe por causa do bloqueador. O que exige, e que não
existia:

- um repositório **sem *rulesets*** dá **1**, e não 0 nem 2
  (`test_repositorio_sem_ruleset_nenhum_e_vermelho`);
- com o privado conforme e o público vazio, o alvo do público dá vermelho e
  **não herda o verde do vizinho** (`test_nao_le_o_ruleset_de_outro_repositorio`)
  — é o defeito, em forma de teste;
- um repositório com *rulesets* mas nenhum com o nome do espelho dá 1
  (`ruleset-ausente`), e dois com o mesmo nome dão 1 (`ruleset-ambiguo`), em vez
  de se escolher um por adivinhação;
- o `id` resolve-se pelo nome, e um `id` declarado que não bate é divergência —
  um *ruleset* apagado e feito de novo tem nome igual e `id` diferente, e entre
  uma coisa e a outra o `main` esteve sem protecção.

**(e2) credencial inválida, transporte `http`:**

```
ruleset: albinoJimy/kamba: GET repos/albinoJimy/kamba/rulesets: 401 Unauthorized

```

**(e3) sem credencial nenhuma, transporte `http`:**

```
$ $RULESET --transporte http
ruleset: albinoJimy/kamba: KAMBA_RULESET_TOKEN nao esta definida. O transporte `http` precisa de um token com `administration: read` (docs/adr/ADR-L003-verificacao-do-ruleset.md).
EXIT=2
```

**(e4) *endpoint* inalcançável — o repositório não existe:**

```
$ $RULESET --root <raiz com um alvo que aponta a um repositorio inexistente>
ruleset: albinoJimy/repositorio-que-nao-existe: `gh api repos/albinoJimy/repositorio-que-nao-existe/rulesets` saiu 1: gh: Not Found (HTTP 404)
EXIT=2
```

**O (e4) mudou de significado com a correcção do C1, e vale explicar.** Antes,
o 404 vinha de pedir um `id` que não existe, e era com ele que se demonstrava o
cenário «*ruleset* apagado». Agora o *ruleset* resolve-se pelo **nome**, e um
*ruleset* apagado deixa de ser 404: a listagem responde, e a resposta é
`repositorio-sem-ruleset` ou `ruleset-ausente` — **saída 1**, que é mais
exacta. O 404 ficou para o que ele de facto é: o repositório não existe, ou a
credencial não o vê. Também isso é fail-closed.

**E um caso novo, que o alvo único não tinha como ter:** uma falha de API no

## 5. O procedimento da janela — para o fundador

**Isto executa-se de uma assentada, numa janela combinada, e repõe-se antes de
sair.** Entre o §5.3 e a sua reversão, e entre o §5.4 e a sua, o `main` do
`albinoJimy/kamba` fica menos protegido do que de costume: o §5.3 retira-lhe um
*required check* e o §5.4 dá *bypass* a quem tem administração. **Não correr com
um PR por fundir nem com uma automação de *merge* activa.**

### 5.0 Convenções destes comandos — leia antes de colar

Tudo corre em **Git Bash, da raiz do repositório**, com o `gh` autenticado numa
conta com administração do `albinoJimy/kamba`.

**Não se usa `make`.** Este anfitrião não o tem — é a primeira linha da tabela
no topo deste ficheiro —, e `make: command not found` não é verde nem vermelho:
é o procedimento a parar no primeiro passo sem o dizer. Define-se antes de
começar:

```bash

```

Confirme que o módulo corre **antes** de tocar em nada:

```bash

```

Se isto disser `No module named ruleset_check`, o `PYTHONPATH` não apanhou o

### 5.1 O estado inicial, e o artefacto que repõe tudo

```bash

#    com `repositorio-sem-ruleset` no `albinoJimy/kamba-plataforma` e o
#    `albinoJimy/kamba` em `[ok]`. Se o alvo do PRIVADO não estiver `[ok]`,

  --jq '{name,target,enforcement,conditions,rules,bypass_actors}' > "$JANELA/antes.json"

# 3. conferir que o que se guardou é exactamente o espelho versionado, pela
#    mesma normalização que o comparador usa — e não por `==` de dicionários,

$PY -c "
```

### 5.2 Como se aplica um corpo alterado, e porque é que o «esperado» não é um palpite

```bash
gh api repos/albinoJimy/kamba/rulesets/24879081 --method PUT --input <ficheiro>.json
```

Os corpos montam-se sobre `$JANELA/antes.json` com Python da biblioteca
padrão — não se assume `jq` instalado.

**Os dois montadores foram corridos a sério, e os corpos que produzem foram
passados ao comparador** — tudo em ficheiros locais, sem tocar em *ruleset*
nenhum. É o que torna os blocos «o que esperar» uma previsão medida e não uma
suposição:

```
corpo montado: 7 -> 6
corpo montado: 1 bypass actor

sem-gate3   -> ['contexto-so-no-ficheiro']
com-bypass  -> ['bypass-actor-no-github', 'campo-divergente']
```

O que falta medir na janela é só a metade que exige o GitHub: que a API aceite
o `PUT` e devolva o que o corpo diz. Os montadores param em vez de escreverem
um corpo que não altera nada — aplicar um `PUT` sem efeito daria um caso de
teste falsamente verde.

## 6. O repositório público, e o que fica por verificar

### 6.1 O repositório público não tem *ruleset* nenhum

```

["pull_request","required_status_checks","deletion","non_fast_forward"]

```

O `[]` não é falta de permissão: a mesma conta tem `admin: true` nos dois
repositórios, e o mesmo comando no `kamba` devolve as quatro regras.

**O `albinoJimy/kamba-plataforma` é público, é onde os PR deste ticket são
abertos, e não tem nenhuma das protecções que o `.github/rulesets/main.json`
descreve.** Nem PR obrigatório, nem *required checks*, nem protecção contra
apagar ou reescrever `main`.

**Na primeira versão deste ticket isto era uma nota de rodapé, e era o
bloqueador.** O verificador tinha um alvo — o privado —, o espelho viajava na
árvore do público, e corrido de um clone do público dizia «conforme» e saía 0.
Uma máquina a certificar a protecção de um repositório que não tem nenhuma é
pior do que não haver máquina: é a frase do §Contexto do ticket («um ficheiro
que parece ser a fonte e não é engana melhor do que a ausência dele») com um
carimbo por cima.

**O que mudou:** o repositório está agora na lista de alvos de
[`../../ci/ruleset.yaml`](../../ci/ruleset.yaml), e a verificação dá
**vermelho** por causa dele (§4.0) — e continua a dar até existir lá um
*ruleset*. **Criar o *ruleset* é acto do fundador**, que o decidiu a
2026-10-18, e o KAM-137 está impedido de alterar *rulesets* por qualquer via. O
passo está no §5.8. A **lacuna 29** do `../ci.md` §7 fica aberta, mas deixa de
depender de alguém se lembrar dela.

### 6.2 O `GITHUB_TOKEN` e a permissão `administration`

**NÃO VERIFICADO por execução.** É a razão que o ADR dá para a verificação não
ser um *gate*, e vale o que vale até ser medida. Como se valida: acrescentar
`permissions: {administration: read}` a um *workflow* de teste e ver se o GitHub
aceita o ficheiro; ou correr `gh api repos/albinoJimy/kamba/rulesets` dentro de
um *job* com o `GITHUB_TOKEN` e ler o código devolvido.

O que **está** medido é a outra metade do argumento: um *token* num *workflow*
exigiria uma referência `secrets.*`, e o `grep` do `../ci.md` §6 continua a
devolver zero porque **nenhum ficheiro de `.github/workflows/` foi tocado**
(§7.3).
