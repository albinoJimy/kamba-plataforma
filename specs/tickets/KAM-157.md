### Contexto

O *gate* 9 prova-se com um **canário**: uma pasta que contém segredos com forma
real, que o teste copia para fora dela e exige que o *scanner* apanhe. Sem ele,
«o *gate* 9 está verde» diria o mesmo sobre um *scanner* que funciona e sobre um
que devolve sempre uma lista vazia. O canário está declarado em
`ci/secrets-allow.yaml` como a única área onde um valor com forma de segredo é
permitido, e se essa entrada desaparecer o *gate* fica vermelho — de propósito.

**Num repositório público, o GitHub tem uma opinião sobre isso.** A *push
protection* do *secret scanning* recusou o `push` com `GH013 — Repository rule
violations`, nomeando duas linhas do canário (um *Slack API Token* e uma *Stripe
API Key*) e oferecendo um URL para desbloquear cada uma. O desbloqueio é
manual, por segredo, feito por uma pessoa na interface do GitHub — e foi assim
que a cópia pública ficou criada: o fundador clicou «It's used in tests» nas
duas.

**O problema não é o `push` que já passou: é o próximo.** Qualquer alteração ao
canário — acrescentar uma classe de segredo nova, que é o que acontece quando o
*scanner* aprende um padrão novo — volta a parar o `push`, e para quem não
souber disto parece um defeito do *pipeline*. Hoje isto não está escrito em
nenhum sítio.

### Objectivo

Quem acrescentar um valor ao canário sabe, **antes de empurrar**, o que vai
acontecer e o que fazer; e a decisão entre as duas vias possíveis está tomada e
registada, com o custo de cada uma escrito.

### Critérios de Aceitação

- [ ] **O comportamento está documentado onde quem mexe no canário o encontra**:
  no `README.md` da pasta do canário e no `docs/ci.md` §3 (*gate* 9), com a
  mensagem exacta do GitHub (`GH013`) e o que ela significa.
- [ ] **A via está escolhida pelo fundador, e o custo de cada uma está escrito**
  (tabela abaixo). Não se escolhe por conveniência de quem empurra.
- [ ] **Se a via escolhida for o `secret_scanning.yml`**: o ficheiro existe, com
  `paths-ignore` limitado **à pasta do canário** e a mais nada, com um comentário
  a dizer porquê, e um teste que falhe se o caminho ignorado deixar de coincidir
  com a área declarada em `ci/secrets-allow.yaml`.
- [ ] **Se a via escolhida for o desbloqueio manual**: o `README.md` do canário
  diz quem o pode fazer e em que ecrã, e o `docs/ci.md` §3 diz que um `GH013`
  num PR do canário **não é** um defeito do *pipeline*.
- [ ] **O *gate* 9 continua a provar-se.** Qualquer via que torne o canário
  invisível ao *scanner* **do repositório** não pode tornar o canário invisível
  ao *scanner* **do gate** — são dois, e é só o do GitHub que está em causa.

### Detalhes Técnicos

**As duas vias, com o custo de cada uma.** Esta decisão é do fundador: é política
de segurança da plataforma, e nenhuma das duas é obviamente melhor.

| Via | O que faz | O que custa |
|---|---|---|
| **A — `.github/secret_scanning.yml` com `paths-ignore`** | O *secret scanning* do GitHub deixa de ler a pasta do canário. O `push` deixa de ser recusado | Cria um caminho no repositório onde o *scanner do GitHub* não olha. Se alguém puser lá um segredo **a sério** — por erro, ou de propósito — o GitHub não o vê. Fica a depender do *gate* 9, que o vê, e da revisão de quem funde |
| **B — desbloqueio manual, caso a caso** | Nada muda no repositório. Cada valor novo com forma real exige um clique de uma pessoa, uma vez | Cada alteração ao canário para o `push` de quem a fizer, e a mensagem não explica que é esperado. É fricção repetida, e fricção repetida ensina a ignorar avisos de segurança |

**A assimetria que decide, se o fundador não quiser decidir pelo custo.** A via A
é reversível num *commit*; a via B não deixa nada escrito no repositório. Mas a
via A **cria** uma área cega permanente no *scanner* da plataforma — e este
conjunto já tem uma regra sobre isso: `ci/secrets-allow.yaml` declara a área do
canário como a única onde um valor com forma de segredo é permitido. Uma via A
limitada a **exactamente** essa área não acrescenta uma excepção nova: alinha o
*scanner* do GitHub com uma excepção que já estava declarada, revista e
verificada por máquina. É essa a **recomendação** — e é uma recomendação, não uma
decisão.

**O que não se faz em nenhuma das vias.** Não se mudam os valores do canário para
«parecerem menos reais»: já se tentou, e é exactamente o que o torna inútil. O
canário prova que o *scanner* apanha a **forma** de uma credencial; um canário
com valores de forma mais fraca prova menos.

### Testes Requeridos

- Unit: se a via for A, um teste que leia `.github/secret_scanning.yml` e
  `ci/secrets-allow.yaml` e falhe se os caminhos não coincidirem.
- Integração: um PR que acrescente um valor com forma nova ao canário, para
  medir o comportamento na via escolhida — num repositório público é a única
  forma de o verificar.
- Manual: a mensagem `GH013` reproduzida e colada no `README.md` do canário.

### Definition of Done

- [ ] Todos os Critérios de Aceitação satisfeitos e demonstráveis.
- [ ] Decisão do fundador registada, com data.
- [ ] Documentação actualizada (`docs/ci.md` §3 e o `README.md` do canário);
  *Conventional Commits*.
- [ ] **Segurança** — a via escolhida não reduz o que o *gate* 9 vê, e o
  *scanner* do GitHub só deixa de olhar para onde `ci/secrets-allow.yaml` já
  declarava.
